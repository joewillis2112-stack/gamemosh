# Code review, 2026-10-08

Independent review of the Claude Studio player runtime and Luau binding. I read the code, and I checked the main claims with probes:

- a Luau probe in Node against the real `web/luau.mjs` and `web/datamodel.js`;
- a headless play scenario through `tools/play.mjs` (`--noshots`);
- a Babylon `NullEngine` check of wedge winding against Babylon's own `CreateBox`.

Findings marked **verified (probe)** were reproduced. **Verified (reading)** means a definite reading of the code with no run. **Uncertain** means I'm not sure of Roblox's behaviour or of the effect.

Files: `web/runtime/{character,players,world,camera,controls}.js`, `web/datamodel.js`, `web/luau.js` (read because it holds the deferred queue), `luau/binding.cpp`, `web/play.js`.

## High

### H1. Wedges render inside-out, and the goldens have that baked in
**world.js:155-164** (`wedgeMesh`). **Verified (probe and goldens).**

- **What's wrong:** the loop turns each triangle so that `(b-a)×(c-a)` points out of the wedge. Babylon's convention is the opposite.
  - In this same right-handed scene, Babylon's own `CreateBox` has `(b-a)×(c-a)` pointing **inward**. Its `ComputeNormals` uses `(p1-p2)×(p3-p2)`, which then points outward.
  - So the wedge is wound against every built-in mesh, and `ComputeNormals` without `{useRightHandedSystem}` gives it **inward normals on all 8 triangles**. Measured: the slope normal is (0, -0.71, +0.71) where it should be (0, +0.71, -0.71), and the bottom normal is +Y.
- **Effect:** back-face culling removes the outer faces. You see the inside of the far faces: floor, back wall and far side triangle, lit with flipped normals.
  - `goldens/play/obby-wedge.png` shows it plainly: the green "wedge" is an open trough (flat floor, vertical back wall, dark side triangle), with no slope surface.
  - `parts-front.png` and `parts-above.png` show the same thing: a vertical rectangle plus a floor strip with a fold, never one planar slope.
- **Why tests pass:** physics uses a convex hull, which ignores winding, so the obby bot still climbs it. The goldens were saved from the wrong render.
- **Fix:** invert the test (`if (dot > 0) swap`) so the winding matches `CreateBox`, then keep the plain `ComputeNormals`. Re-judge and re-save `parts-front`, `parts-above`, `obby-wedge` and `obby-overview`. Add a code check to the gate: for every face of a generated mesh, the normal · (face centre − solid centroid) > 0, and the winding matches `CreateBox`.

### H2. `Disconnect` doesn't cancel deferred events already queued; the freed registry ref is then called
**binding.cpp:284-292, 769-782; luau.js:9-17.** **Verified (probe).**

- **What's wrong:** the JS queue holds `[ref, args]`.
  - `conn_disconnect` calls `lua_unref(ref)`. Luau stores the free-list index (a number) in that slot and hands the slot to the next `lua_ref` (`lapi.cpp` `lua_ref`/`lua_unref`).
  - Any fire still queued for that connection then runs `cs_fire(ref)` on whatever the slot holds now.
- **Failing scenarios (probe output):**
  ```lua
  local c; c = p.Changed:Connect(function(k) print("A got", k); c:Disconnect() end)
  p.Transparency = 0.5; p.CanCollide = false
  -- A got Transparency
  -- ERR attempt to call a number value
  ```
  If the handler connects something after disconnecting (or calls `task.wait`, which refs its thread), the slot is reused and **a different function runs with this event's arguments**:
  ```
  A got Transparency
  B (ChildAdded handler) called with CanCollide
  ```
  Roblox: a disconnected connection never runs again, even for deferred events.
- **Fix:**
  - Queue the connection id, not the ref.
  - In `flush`, skip the entry if `dm.conns` no longer has the id.
  - Keep a JS-side id → ref map, and only `lua_unref` after the entry is removed and no queued fire for it remains (or just check the id at flush time).
  - Do the same for `dm.destroy` (it deletes the conns, but queued fires still run, which is probably fine for `Destroying` only).

### H3. `Touched` never fires for collidable parts met from the side or head-on
**players.js:189** (body box `h: [1, 2.525, 0.6]`) against the capsule radius at **character.js:23, 192** (`Radius: 1`). **Verified (probe).**

- **What's wrong:** the controller keeps the capsule centre at least radius + skin away from a wall. The touch box only reaches 0.6 forward and 1.0 sideways.
- **Probe:** an anchored 12×10×1 wall 8 studs ahead, with a `Touched` print, and the player walking into it for 150 frames.
  - The player stopped at z = 6.36. The wall face is at 7.5, so the centre sits 1.14 from it.
  - The box front was at 6.96, and **no `Touched` fired**.
  - The same holds sideways (1.0 against ≥1.05) and for ceilings (the capsule top equals the box top).
  - Only floors (the box reaches 0.05 below the soles) and `CanCollide=false` parts touch.
- **Effect:** walls that kill, collidable checkpoint pillars, door buttons and "touch the wall to win" pads never fire. Roblox fires `Touched` on physical contact.
- **Fix:** make the touch volume enclose the collision shape plus a skin.
  - Half-extents of at least `Radius + 0.15` in x and z, starting at the soles and topping out at least 0.1 above the capsule top.
  - Better: use the controller's contact manifold, or a Havok shape query with the capsule grown by the skin.
  - Add a scenario with a wall and a ceiling `Touched`.

### H4. The dead-body footprint measures the standing pose, so `clearFall` doesn't protect the lying body
**character.js:184, 221-222, 81-82; players.js:107-134.** **Verified (probe).**

- **What's wrong:** `measurePose` runs in the constructor before `anim.play()` has ever set `this.fade`.
  - `update(0)` computes `step = 0 / undefined = NaN`, and `Math.max(1, 1 - NaN)` is `NaN`, so the layer weight is `NaN`.
  - `a.pw > 0` and `a.qw > 0` are then false, so every node stays at **rest**.
- **Measured in the running game:**
  - `deadBox` as built: min (-1.48, 0, -0.74), max (1.48, 5, 0.74). That's the standing box.
  - The real die pose, measured with `fade` set: min (-1.48, -0.65, -5.19), max (1.48, 0.83, 0). The body lies 5.2 studs behind the feet.
- **Effect:** `clearFall` checks a 5-stud-tall column at the feet instead of the strip behind the character. A body dying with its back to a wall or step lies through it. PLAN.md's claim ("the dead body is placed so its measured lying footprint doesn't cut into parts") doesn't hold.
  - It can also turn or shift the body needlessly when something is beside the standing box.
- **Fix:** set `this.fade = 0.15` in the `Animator` constructor, or guard `const step = this.fade > 0 ? dt / this.fade : 1`. Then re-check `death.png` and add a test that `deadBox.max.y < 1.5`.

## Medium

### M1. Cylinders collide as boxes
**world.js:191.** **Verified (reading).**

- **What's wrong:** `type` is `SPHERE` for a Ball, `CONVEX_HULL` for a wedge, and `BOX` for everything else, including `Cylinder`.
- **Failing scenario:** obby stage 4 has upright cylinder pillars. The player can stand on air at the square corners past the round top, and grazes invisible corners when passing beside a pillar.
- **Fix:** use `PhysicsShapeType.CYLINDER` (axis along local X, matching the baked mesh) or `CONVEX_HULL`.
- The touch test (players.js:194-196) also treats cylinders and wedges as their bounding box. A wedge kill or touch pad fires in the empty space above its slope. Add a wedge (half-space) test and a cylinder test.

### M2. Every property change rebuilds the Havok body, the decal planes and the decal textures, and unanchored parts lose their momentum
**world.js:172-195, 197-212** (`changed` → `apply` → `decals()` + `body()`). **Verified (reading).**

- **What's wrong:** any `dm.set` on a part (Color, Transparency, Material, Reflectance, even an equal value; see M3) does all of this:
  - disposes and recreates the `PhysicsAggregate`;
  - disposes every decal plane, its `PBRMaterial` and its `Texture`, then rebuilds them from the data URL.
- **Failing scenarios:**
  - A rainbow part (`part.Color = Color3.fromHSV(t%1,1,1)` every frame, very common in Roblox games) recreates a physics body every frame.
  - A part with a Decal that changes Color re-decodes its PNG every frame.
  - An unanchored ball whose Color changes stops dead each time, because its velocity is lost.
  - PLAN.md knows about moving anchored parts. It doesn't mention Color, Transparency or decals.
- **Fix:** split `apply` by key:
  - Color, Material and Reflectance change only the material.
  - Transparency changes only visibility.
  - Decal rebuilds only when a Decal changes.
  - Position and Orientation of an anchored part move the body (`setTargetTransform` or a kinematic body).
  - Size, Shape, CanCollide and Anchored rebuild the body.
- Also, **world.js:47-59** caches one `PBRMaterial` per material|colour string and never disposes any. A colour-cycling part adds a material on every distinct colour (an unbounded leak). Use a bounded cache, or one material per part with `albedoColor` updated in place.

### M3. `Changed` (and the watchers) fire when the value didn't change
**datamodel.js:201-207.** **Verified (probe):** two identical `p.Anchored = false` writes fired `Changed` twice.

- Roblox fires `Changed` and `GetPropertyChangedSignal` only on a real change.
- Besides the API difference, every no-op write takes the full rebuild path in M2.
- **Fix:** in `set`, return early when the value is equal: `===` for primitives, and component-wise for `V3` and `C3`. `Parent` already short-circuits.

### M4. `ValueBase.Changed` passes the property name instead of the new value
**datamodel.js:206.** **Verified (probe):** `IntValue.Changed` gave `"Value"`.

- Roblox's `IntValue`, `NumberValue`, `BoolValue`, `StringValue` and the other ValueBase classes fire `Changed(newValue)`.
- **Failing scenario:** the usual leaderstats HUD, `stage.Changed:Connect(function(v) label.Text = v end)`, shows "Value".
- **Fix:** for `isA(cls, 'ValueBase')` (add that base class), fire `Changed` with `[value]`, and only when `key === 'Value'`.

### M5. `WaitForChild` doesn't wait
**datamodel.js:71.** **Verified (probe):** `f:WaitForChild("Later")` returned `nil` while the child was being created 0.05 s later.

- **Failing scenario:** `player:WaitForChild("leaderstats")` in one script, with another script creating it in `PlayerAdded`, gives nil and then "attempt to index nil".
- **Fix:** implement it in the binding as a yield. Take a thread ref, register a `ChildAdded` watcher on that instance for that name, and resume when it arrives. Honour the optional timeout, and warn after 5 s as Roblox does.

### M6. Shared metatables are writable from any script: one script can rewrite `Instance`, `Color3` and `EnumItem` for every script
**binding.cpp:591-660, 718.** **Verified (probe).**

- **What's wrong:** `luaL_sandbox` freezes the globals and the string metatable. It doesn't freeze the `luaL_newmetatable` tables, and none of them sets `__metatable`.
- **Probe:** `getmetatable(workspace).__tostring = function() return "hijacked" end` succeeded. A second script then printed `tostring(workspace)` as `hijacked`, and every later `ChildAdded` print showed `hijacked`.
- The same access also reaches the C functions with arguments they don't expect:
  - `getmetatable(Enum.Material).__index({}, "x")` makes `enumtype_index` build `std::string(nullptr)` (binding.cpp:538);
  - `enumitem_index` and `enumitem_tostring` dereference a null `to_enum` result.

  In wasm, address 0 is readable, so these produce garbage rather than a clean error.
- **Fix:** set `__metatable = "The metatable is locked"` on every metatable, as Roblox does, and `lua_setreadonly` them before `luaL_sandbox`. Check for null `to_enum`, and for a missing `__name` in `enumtype_index`.

### M7. With `CharacterAutoLoads = false`, an avatar is still drawn, walks and is followed
**camera.js:58; players.js:37-38; play.js:55-56.** **Verified (reading).**

- **What's wrong:**
  - `join()` hides the character, but `FollowCamera.update` calls `char.setVisible(!first)` every frame and shows it again.
  - `tick` steps the controller whether or not a character exists.
- **Effect:** a menu-first game (CharacterAutoLoads off until the player presses Play) shows a controllable blocky figure at (0,0,0), with no Model or Humanoid behind it.
- **Fix:** keep a `hasCharacter` flag in Players. Skip `player.setInput` and `step` when it's false, and make the camera's visibility `!first && players.hasCharacter`. Equivalently, have the camera only hide for first person and never force visible.

### M8. Touch detection is a full scan with heavy allocation every frame
**players.js:187-209, 226-236** (and `clearFall` 117-123). **Verified (reading).**

- **What's wrong:** for every part in `world.parts` (baseplate, decoration, all obby pieces) on every frame, `boxBox` builds 15 axis arrays, two `reduce` closures per axis, and the `rotAxes` and `c`/`h` arrays.
- **Effect:** 500 parts cost tens of thousands of short-lived objects per frame. That means GC pauses on a mid-range phone, growing linearly with the place.
- **Fix:**
  - Broad-phase first: compare the part's bounding-sphere radius (|Size|/2) with the distance to the body.
  - Cache each part's axes and half-extents in its `world.parts` entry, updated in `apply` and `syncFromPhysics`.
  - Write SAT with scalar math, no arrays.
  - Or query Havok for overlaps against a slightly grown capsule.

### M9. Character death and respawn don't end touches
**players.js:71, 170.** **Uncertain (exact Roblox behaviour).**

- **What's wrong:** while dead, `touches()` isn't run, and `spawn()` clears `touching` without firing `TouchEnded` for the parts the old body touched.
- **Failing scenario:** a "players on the pad" counter (+1 on `Touched`, −1 on `TouchEnded`) drifts up by one on every death that happens on the pad.
- I believe Roblox fires `TouchEnded` when the touching part is destroyed or leaves, but I haven't checked.
- **Fix:** before clearing `touching`, fire `TouchEnded` (part side) for each part that isn't destroyed.

### M10. A script destroying its character leaves the runtime driving dead instances
**players.js:155-173.** **Verified (reading)** for this runtime; **uncertain** what Roblox does exactly.

- **What's wrong:** after `player.Character:Destroy()`, `this.root` and `this.humanoid` are destroyed but still used.
  - `syncRoot` writes to them.
  - `touches()` fires `Touched` with the destroyed root as `hit`, so the usual `hit.Parent:FindFirstChild("Humanoid")` errors because `hit.Parent` is nil.
  - Nothing respawns the player, unless they fall below −500.
  - The figure stays visible and controllable.
- **Fix:** watch the character model's `Parent`. When it leaves the workspace, treat it as a death (hide, fire nothing on the stale instances) and respawn after `RespawnTime` if `CharacterAutoLoads` is on.

### M11. Memory that never comes back: handles and handler refs
**datamodel.js:165, 194-200; binding.cpp:274.** **Verified (reading).**

- `byHandle` only grows, so every destroyed Instance (with its props and children arrays) is kept forever.
- `dm.destroy` deletes the instance's connections, but each handler's Luau ref (`lua_ref` in `signal_connect`) is never released. Each destroyed coin with a `Touched` handler leaks its closure and upvalues.
- A game that spawns projectiles or coins grows without bound over a long session.
- **Fix:**
  - On destroy, tell the binding to `lua_unref` the refs of the deleted conns (export `cs_unref`, or return them through the channel).
  - Free the handle slot once no Luau userdata holds it: the weak cache tells you via a `__gc`-less finaliser, so use a `lua_newuserdatadtor` destructor that calls back into JS.
- Related: `RBXScriptConnection.Connected` stays `true` after the instance is destroyed (binding.cpp:307). Roblox reports false.

### M12. Default jump uses `JumpPower` 50 (6.37 studs); new Roblox places use `JumpHeight` 7.2
**datamodel.js:121 (`UseJumpPower: true`), players.js:140.** **Uncertain.**

- My understanding is that new places set `StarterPlayer.CharacterUseJumpPower = false` with `CharacterJumpHeight = 7.2`, so a default character jumps 7.2 studs.
- If that's right, obby gap tuning and "jump 6.369" are calibrated to the older default.
- Check Roblox's StarterPlayer reference before changing anything.

## controls.js and play.js

- **controls.js:** no correctness bugs found. The dead zone and ramp normalisation, multi-touch bookkeeping and keyboard normalisation all check out.
